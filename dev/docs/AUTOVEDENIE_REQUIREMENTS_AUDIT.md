## Контракт реализации тренажёра

Следующие пункты являются инженерной адаптацией источников к имеющейся native модели. Они не воспроизводят закрытый заводской оптимизатор.

1. **Режим 0.** Расчётная цель получается из достоверного маршрута, профиля, действующих ограничений, задания скорости/расписания и фактического состава. Нужны разгон, удержание, выбег и предварительное торможение. Наличие меню, одной положительной силы или расчётной рекомендации не подтверждает управление.
2. **Режим 1.** Признак `PoUdaleniyu` хранить отдельно от источника цели, используя определение S2 выше. Сведения о хвосте впереди идущего поезда сами по себе не доказывают этот режим. Численная скорость/точка остановки в §6.2 не заданы. Применять общую проверенную цель native САУТ/сигнализации можно как адаптацию, с явным происхождением данных; статическая карта не удостоверяет живой АЛСН. При отсутствии необходимого подтверждения автоматический режим 1 недоступен. Не угадывать скорость 20/30/40 км/ч либо точную последовательность автоматического включения по смене АЛСН.
3. **Режим 2.** Известно название и наличие интенсивности. Связь с `arrivalTime`, конкретная формула нагонного задания и допустимый диапазон не установлены. Не обозначать собственный таймерный алгоритм как заводской «нагон». До получения контракта отображать недоступность автоматического режима 2 либо явно отдельную учебную функцию.
4. **Советчик.** Может показывать расчёт при пригодных данных, но не владеет исполнительными командами. Фактические режим/позиция/токи должны читаться из native выходов, а не копироваться из плана.
5. **Включение.** Только новое явное событие клавиши 5 и подтверждённые данные/готовность. Не ставить запрос в очередь до восстановления готовности и не включать АВП после восстановления связи, снятия аварии или возврата органов в нейтраль. Состояние редактора не равно принятому заданию.
6. **Арбитраж.** Native ЭПК/экстренное/САУТ и ручные органы сохраняют свои выходы. Снятие владения АВП не должно обнулить уже исполненную ручную команду. Собственную тормозную команду АВП и несистемное давление ТЦ различать по происхождению/состоянию команды, а не по одному ненулевому давлению.
7. **Исполнение.** Только проверенный native интерфейс задания; без записи скорости или замены силы синтетической. На каждом шаге подтверждать фактический ответ электрической и поездной модели, ограничивать частоту/размах команд по её возможностям. Числа процентов/позиций на экране не являются доказательством бинарного ABI.
8. **Выход/ошибка.** Убрать только собственные команды и своё владение. Причину отказа сохранить и показать; новый вход требует команды. При неверных координате/составе/профиле/устаревшей цели не продолжать скрытую автоматическую тягу.

### Целый состав и прогноз торможения

В S1–S3 не найдено явного правила снятия ограничения после прохода хвоста; оно не приписывается заводскому алгоритму. Для требуемого поведения тренажёра установить отдельный проверяемый контракт: ограничение на интервале пути действует, пока его пересекает любая часть физического состава. Увеличение допустимой скорости допускается только после выхода хвоста. Для обратного направления сначала нормализовать ось движения; нельзя применять только сравнение возрастающих километров.

Длина/масса должны соответствовать действующему native поезду; введённые цифры не заменяют физический состав. Прогноз торможения включает скорость, профиль под составом, тормозную возможность, задержку и отпуск. Формула вроде `v²/(2a)` является модельной оценкой, а не найденной заводской формулой. Предварительное торможение проверяется фактическим прохождением начала ограничения с допустимой скоростью, удержанием ограничения до хвоста и native отрицательной силой/давлениями.

Автоматическая остановка у конца учебного участка — адаптация для сценария/границы модели. Она не называется штатным прибытием ИСАВП-РТ на конечную станцию: S2 требует там ручной контроллер. После такой остановки не должно происходить автоматического повторного разгона либо отмены независимого тормоза.

### Режимы 0/1/2 и явные источники оператора

Названия в S4 сохраняются: **0 — обычный, 1 — по удалению, 2 — нагон**. В C# им соответствуют `Ordinary`, `SignalFollowing`, `CatchUp`; внутреннее имя `SignalFollowing` не означает следование по измеренной дистанции до другого поезда. Определение режима 1 остаётся сигнальным правилом S2: один жёлтый за ближайшим зелёным. В ядре для него требуется отдельное подтверждённое сигнальное задание. Production host такого живого источника сейчас не имеет и отказывает автоматическому режиму 1. Автоматический режим 2 также отказывает, потому что алгоритм нагона не установлен. Текущая интеграция допускает попытку включения только обычного режима 0 при пригодном задании и всех gates готовности.

В host два разрешения изначально выключены: **«Учебное разрешение движения»** и **«Программный пульт ТЭД»**. Второе отдельно требует явного выбора ТЭД 1 и ТЭД 2; эти switches тоже выключены по умолчанию. Ни `Attach`, ни ядро не включают двигатели самостоятельно. Изменение любого такого выбора отменяет владение АВП и требует повторного нажатия 5. Учебное разрешение — явное условие сценария, а не полученный сигнал АЛСН/САУТ; статическая PDF-карта его не удостоверяет.

Программный пульт — отдельная адаптация операторского ввода. Его scope временно передаёт выбранные пользователем значения в `TPult.Btn.TD_1_Btn/TD_2_Btn` (`TPult+0x34/+0x38`) при чтении готовности и перед исходным `ProceedPult`, с guards и восстановлением собственных значений. Это не запись производных групп ТЭД, контакторов, разрешений, тока, силы или скорости. Независимое возбуждение продолжает поступать через штатный вход кабины `form+0x3FC` → `TPult+0x2C`, с проверкой фактического `Tyga+0x16`.

Для физического аппаратного пути установлена отдельная статическая цепь: `Init/ConstHardware.pas:48–51` задаёт ВВ 32–35; `Init/Hardware1.cbn:699–766` задаёт четырёхзначные селекторы ТЭД 1/2, порт 49, биты 8/9 и 10/11. `TComm2ES6.UpdateButtonsHW` (Communication RVA `0x2B0FF8`) читает `THardwares.GetValueParam(32/33)` → внешний `GetInt` → аппаратную запись → `TPult+0x34/+0x38`. Запись кэша аппаратной записи перетирается getter; штатный `THardwares.SetIntValue` для этих ВВ ничего не делает. API `GetFunction/GetInt/SetInt/SetValue` найден в `Cbndll.dll` и `DLL_BBT.dll`, но фактически загруженный provider, `functionId` и безопасный input-write через него отдельным прогоном пока не подтверждены. Программный пульт не выдаётся за проверенную замену этого аппаратного provider.
